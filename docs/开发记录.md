### 三个贯穿全程的环境前提

1. **必须 `unset ELECTRON_RUN_AS_NODE` 再跑 electron-builder。**  
   这台机器的宿主环境默认设了 `ELECTRON_RUN_AS_NODE=1`，Electron 会被当成普通 Node 跑，  
   构建/启动行为都不对。所有构建命令前面都加了 `unset`。
2. **两个原生依赖都是 N-API 预编译，不需要本机编译环境。**  
   `uiohook-napi` 自带 `prebuilds/{win32-x64,linux-x64,darwin-*}/uiohook-napi.node`；  
   `@nut-tree-fork/libnut-*` 是按平台拆分的预编译包。  
   所以 `build.npmRebuild` 设成了 `false`，避免 electron-builder 去尝试重编译。
3. **`npm install` 很慢（约 17 分钟，428 个包）。**  
   瓶颈是 Electron 二进制从 GitHub 下载。后续构建统一用  
   `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` 加速。

## 1. 阶段一：打包成 Windows exe

**原始需求**：跨系统鼠标共享项目，用 npm，打包成 exe，跑 `npm install` + `npm run build:win`。

### 1.1 直接跑通 ≠ 能用

`npm install` 和 `npm run build:win` 本身能跑通，产物 `dist/NetMouse-0.1.0-win.exe`  
（NSIS 安装包，82 MB）。但**装出来的程序是不能用的**——打包前发现并修了 3 个阻塞问题：

#### 问题 1：config.json 是 JSONC，代码却用 `JSON.parse`

仓库里的 `config.json` 带 `//` 注释（README 里也写的是 jsonc），  
而 `src/config.js` 用的是严格 `JSON.parse`。结果**应用一启动就崩**，  
和打不打包无关。

**修法**：给 `src/config.js` 加了 `stripJsonComments()` / `stripTrailingCommas()` /  
`parseJsonc()`。手写扫描而不是用正则，是为了不误伤字符串里的 `//`（例如 URL）。

#### 问题 2：打包后配置无法修改

原来 `config.json` 被打进只读的 `app.asar`，装完永远只能用硬编码默认值  
（`role=server`、`host=""`、`password=change-me-strong-password`），两台机器根本没法配。

**修法**：改成按顺序查找配置文件，并用 `extraFiles` 把 `config.json` 放到  
`NetMouse.exe` 旁边，装完直接改那个文件。`canWriteTo()` 对 `app.asar` 内的路径直接返回 false。

#### 问题 3：托盘图标是空的

`main.js` 用的是 `nativeImage.createEmpty()`，Windows 上等于没有图标——  
纯托盘应用会变成**找不到也退不出的僵尸进程**。

**修法**：用 Python 生成图标（`build/icon.png` 256px、`src/assets/tray.png` 32px），  
并在托盘菜单加了 **Open config file / Open config folder**。

### 1.2 构建环境踩的坑

| 现象                                                    | 原因                                                  | 解法                                                                                                    |
| ----------------------------------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 构建报 `Cannot create symbolic link ... libcrypto.dylib` | `winCodeSign` 7z 包里含 2 个 macOS 符号链接，非管理员/未开开发者模式建不了 | 把已成功解压的目录改名成 app-builder 期望的缓存名 `%LOCALAPPDATA%\electron-builder\Cache\winCodeSign\winCodeSign-2.6.0` |
| Electron 被当普通 Node                                    | 宿主 `ELECTRON_RUN_AS_NODE=1`                         | 构建前 `unset`                                                                                           |

关于 winCodeSign：读了 app-builder 的源码（`pkg/download/*.go`）确认  
**`CheckCache` 只判断目录是否存在，不校验内容**，所以直接改名即可绕过，  
不需要管理员权限。`nsis` / `nsis-resources` 包里没有符号链接，能正常下载。

### 1.3 验证方式（可复用）

纯托盘应用不能直接启动（会挂全局键鼠钩子），所以用：

```bash
ELECTRON_RUN_AS_NODE=1 dist/win-unpacked/NetMouse.exe \
  -e "require('<...>/app.asar/src/config.js').loadConfig()"
```

实测确认：配置正确解析到 `win-unpacked\config.json`，`role=server` 和分辨率都读出来了，  
原生模块也已从 asar 正确解包。

### 2.2 顺手修掉的 3 个真 bug

这三个都是**原代码就有的**，不是改造引入的：

1. **重启节点必崩。** `server.close()` 不会释放监听端口（存活连接还在），  
   重启必 `EADDRINUSE`。→ 现在会 destroy 掉存活 socket。
2. **重复转发。** `server-input.js` 每次创建都在 `uIOhook` 上叠加一套监听器且从不解绑，  
   重启后事件会被转发两遍。→ 改成 hook 进程级单例 + `stop` 时 `uIOhook.off()` 解绑。
3. **无对端时卡死。** 鼠标碰到边缘就进 captured，即使没有 client 连着也不释放。  
   → 加了 `hasPeer()` 门槛。

### 2.3 两个容易踩的语义（已写进 README 和界面提示）

1. `layout.screenWidth/Height` 是 **server 的分辨率**，**两台机器都填 server 的值**。  
   server 用它做边缘判定；client 用它把收到的坐标换算到本机屏幕  
   （本机分辨率由程序用 nut-js 自动检测，不用填）。
2. `layout.edge` 也是 **server 的共享边**，两端填同一个值。  
   client 朝向服务器的那条边由程序自动取反  
   （server 共享 `right` ⇒ client 从自己的 `left` 边把控制权还回去）。

界面里这两个字段的说明文字会**随角色切换**，就是为了避免填错。

### 2.4 图形界面功能

- 参数编辑：角色、监听端口、对端地址/端口/密码（带显示切换）、共享边缘（九宫格点选）、  
  分辨率、日志级别、自启动、关闭窗口是否最小化到托盘
- 实时状态：运行中/已停止、对端连接状态、当前是本地还是远程控制
- 实时日志：logger 的环形缓冲，打开界面能看到之前的记录
- 环境提示：Wayland / 缺 DISPLAY / 缺 xdotool 直接告警
- 按钮：保存、保存并重启、启动/停止/重启、检测本机分辨率、打开配置文件/文件夹、重新载入
- 托盘菜单同步这些操作；单实例锁（两个实例会抢全局钩子和端口）

### 2.5 Ubuntu 支持的关键点

**配置可写性**——这是 Linux 上最关键的问题。AppImage 的程序目录是只读挂载、  
deb 装到 `/opt` 是 root 所有，原来「配置放 exe 旁边」在 Linux 上根本存不进去。

所以配置查找顺序改为：  
`$NETMOUSE_CONFIG` → userData → 程序同目录 → `<resources>` → asar 兜底；  
写回时优先写读到的文件，不可写就自动落到用户数据目录。界面会显示实际路径。

其余：

- 多尺寸图标（16~512）、desktop entry、`deb.recommends: ["xdotool"]`
- 托盘在 Linux 可能没有 appindicator 支持——失败会自动降级为「只用窗口」，  
  不会变成找不到的僵尸进程
- 日志时间戳改用本地时区（原来是 UTC）

### 2.6 验证方式

三种手段，后续几个阶段一直在用：

1. **打包后模块加载验证**  
   `ELECTRON_RUN_AS_NODE=1 NetMouse.exe -e "require('...app.asar/src/config.js')"`
2. **离屏渲染截图**：临时 Electron 脚本 + stub preload + `capturePage()`，  
   用来检查两种角色下的排版和文案。
3. **真机 E2E（CDP）**：`NetMouse.exe --remote-debugging-port=9223`
   - Node 22 内置 `WebSocket` 走 CDP `Runtime.evaluate` 调 `window.netmouse.*`，  
     验证 IPC 与 DOM。
   > **注意**：CDP 里 `await` 必须包在 `(async () => ...)()` 里，  
   > 裸顶层 `await` 会报 `SyntaxError: missing ) after argument list`。
   >
   > **务必用 `NETMOUSE_CONFIG` 指向临时配置**，否则 `saveConfig` 会覆盖仓库里的  
   > `config.json`（这个坑后面真的踩到了，见 3.5）。

结果：打包后的 `NetMouse.exe` UI 从 asar 正常加载、IPC 全部通、  
`saveConfig`/`reloadConfig` 往返正确、client 角色的提示文案正确。  
`selftest` 通过（96 键位映射）。

## 3. 阶段三：免安装便携版

**需求**：「能不能免安装，做成工具即可」。原来只有 NSIS 安装包。

### 3.1 关键问题：portable exe 每次启动都会解包到 temp

electron-builder 的 `portable` 目标产出的单文件 exe，**每次启动都会把自己解包到  
temp 目录再运行**。所以「exe 同目录」指的是临时解包目录——配置写那儿等于每次开机都重置。

electron-builder 为此传了一个环境变量 `PORTABLE_EXECUTABLE_DIR`，  
指向**真实 exe 所在目录**。便携版必须用它。

### 3.2 配置查找顺序（最终版）

1. `$NETMOUSE_CONFIG`
2. **便携目录**：`NETMOUSE_PORTABLE_DIR` → `PORTABLE_EXECUTABLE_DIR` → `APPIMAGE` 所在目录
3. userData（`%APPDATA%\NetMouse\` / `~/.config/NetMouse/`）
4. 程序同目录
5. `<resources>/config.json`
6. 打进 asar 的默认副本（兜底）

写回规则：读到的文件可写就写回它；否则先试便携目录；再不行落 userData。

### 3.3 改动

- **`src/config.js`**：新增 `portableDir()` / `isPortable()`；  
  `candidatePaths()` 把便携目录插在 `NETMOUSE_CONFIG` 之后；  
  `resolveWritePath()` 加便携目录回退；`loadConfig()` 暴露 `cfg.portable` / `cfg.portableDir`。
- **`src/main.js`**：新增 `ensurePortableConfig()`——便携模式首次启动时在**真实 exe 旁边**  
  用 `flag:"wx"` 生成 `config.json`（内容取自打包进去的那份，**保留注释**；  
  目录只读时静默失败，后续自动落 userData）。  
  新增 `configFileToOpen()`——文件不存在就先写出来，  
  保证「打开配置文件/文件夹」永远有东西可开。
- **`src/ui/*`**：「配置文件」卡片加「免安装 · 便携版」标记，说明里写明配置就在程序文件夹。
- **`package.json`**：`build:win` 改为 `electron-builder --win portable zip --x64`；  
  新增 `build:win:installer` 打 NSIS；各目标 `artifactName` 分开，避免 portable 和 nsis 撞名。

### 3.4 验证（在真实产物上做）

把 portable exe 拷到一个**全新空文件夹**运行：

- 约 3 秒后在它旁边自动出现 `config.json`，内容 = 打包进去的带注释默认值 ✔
- CDP 实测 13 项全过：`runtime.portable=true`、configPath/writePath 都指向 exe 同目录、  
  `saveConfig` 落盘位置正确、界面出现「免安装 · 便携版」标记、  
  reload 后 role/host/分辨率/日志级别全部回读正确 ✔
- **顺带撞见真机联调**：另一局域网客户端连上了这个便携版 server  
  （日志 `peer authenticated` → `remote client connected`），等于免费做了一次真实互通验证 ✔
- 测试完已 `taskkill`，24800 端口释放。

### 3.5 踩到的坑：测试脚本覆盖了仓库配置

`saveConfig()` 会写「读到的那个文件」——在开发目录里那就是**仓库的 `config.json`**。  
一个 round-trip 测试把出厂默认覆盖成了 `role=client / host=<测试地址>`，  
注释也全丢了，而这个项目**不是 git 仓库**，没法回滚。

已手工恢复成正确默认（`role=server`、`host` 留空、JSONC 注释齐全）并重新打包。  
**纪律**：任何会写配置的测试，必须把 `NETMOUSE_CONFIG` 指向临时文件。

## 4. 阶段四：Ubuntu 便携版

**需求**：「帮我把 ubuntu 的便携版也打包好」。

### 4.1 结论先行：AppImage 在这台 Windows 上打不了

AppImage 是 Linux 上最标准的「单文件免安装」形态，但它**无法从 Windows 交叉构建**。  
实测确认了三条，按发现顺序：

1. **`mksquashfs` 是 Linux ELF。**  
   AppImage 目标需要执行 `mksquashfs`，它随 `appimage-12.0.1.7z` 一起下载。  
   在 Windows 上直接跑：
   ```
   cannot execute binary file: Exec format error
   ```
2. **解压 `appimage-12.0.1.7z` 本身就失败。**  
   包内有符号链接（`libopenjp2.so` → `libopenjp2.so.2.3.0`），  
   非管理员/未开开发者模式建不了，报  
   `Cannot create symbolic link ... libopenjp2.so`  
   （和阶段一的 winCodeSign 是同一类问题）。
3. **本机没有替代环境。** 没有 Docker；`wsl.exe` 被安全策略列入黑名单，无法使用。

> **正确做法**：在 Ubuntu 上执行 `npm run build:linux:appimage`（配置已就绪，一条命令）。  
> 已把这条限制写进 README，避免以后再试。

### 4.2 替代方案：tar.gz 绿色包 + 单文件自解压 .run

既然 AppImage 打不了，就用能在 Windows 上可靠产出的两种形态：

| 产物                                | 形态                                             |
| --------------------------------- | ---------------------------------------------- |
| `NetMouse-<ver>-linux-x64.tar.gz` | 绿色包，解压后运行 `netmouse.sh`                        |
| `NetMouse-<ver>-linux-x64.run`    | **单文件**，`chmod +x` 后双击；首次运行解压到旁边的 `.netmouse/` |

好消息是**代码层面不用改**：`uiohook-napi` 自带 `linux-x64` 预编译，  
`@nut-tree-fork/libnut-linux` 也已经在 `node_modules` 里，  
两个 `.node` 都验证过是真 ELF。所以 `--linux dir` 交叉构建出的目录是完整可用的。

### 4.3 关键坑：从 Windows 打 tar 包会丢失 Unix 权限位

electron-builder 自己打出来的 `tar.gz`，**里面所有文件都是 0644**：

```
NetMouse-0.1.0-linux-x64/netmouse           0o644   ← 主程序，不可执行
NetMouse-0.1.0-linux-x64/chrome-sandbox     0o644   ← 需要 setuid，权限错
```

原因很直接：Windows 文件系统没有 Unix 权限位，归档时无从记录。  
**这样解压出来的包根本跑不起来。**

**修法**：不让 electron-builder 归档，而是自己写脚本。  
`scripts/package-linux-portable.py` 把 `dist/linux-unpacked` 重新归档，显式写回：

| 路径                        | 模式               |
| ------------------------- | ---------------- |
| `netmouse`                | 0755             |
| `chrome_crashpad_handler` | 0755             |
| `chrome-sandbox`          | **4755**（setuid） |
| `netmouse.sh`             | 0755             |
| 所有目录                      | 0755             |
| 其余文件                      | 0644             |

### 4.4 关键坑：Linux 沙箱

Electron 的 `chrome-sandbox` 必须是 `root:root` 且权限 `4755`。  
绿色包**没法自带这个权限位**（只有 root 能设置）。

而 Electron 的行为是：**如果 `chrome-sandbox` 存在但配置不正确，它会直接 abort，  
不会自动降级**：

> The SUID sandbox helper binary was found, but is not configured correctly.  
> Rather than run without sandboxing I'm aborting now.

**修法**：`build/netmouse.sh` 启动脚本会检测  
`stat -c '%u:%a' chrome-sandbox` 是否为 `0:4755`：

- 是 → 正常启动（完整沙箱）
- 否 → 加 `--no-sandbox` 启动，并打印恢复完整沙箱的两条命令

（AppImage 和 deb 由各自的启动器处理这个问题，不需要手动管。）

### 4.5 自解压 .run 的实现坑

`.run` 的结构是「shell stub + 直接拼接的 tar.gz」，stub 用  
`tail -c +N "$0" | tar xz -C "$APPDIR" --strip-components=1` 解出负载。

坑在于：`tail -c +N` 是 1-based，N = stub 字节长度 + 1；  
而**N 自己的位数会改变 stub 的长度**，从而改变 N。所以要迭代求不动点：


```
base   = len(stub 去掉占位符)
digits = 1
loop:  offset = base + digits + 1
       if len(str(offset)) == digits: break
       digits = len(str(offset))
```

不能「先按固定宽度占位、替换完再算」——那样算出来的偏移是错的。

### 4.6 新增文件

## 5. 阶段五：Linux 双机联调 + 多屏坐标修复（2026-10-09）

**背景**：从「在 Linux 工作站上把 v1 跑起来」开始，到与 Windows 测试虚拟机真实联调，  
暴露出一连串**运行时**问题。这一阶段全部是在真实两台机器上发现的，静态检查看不到。  

### 5.1 Linux GUI 起不来：`node_modules` 里装的是 Windows 版 Electron

上传过来的 v1 项目，`node_modules/electron/dist/` 里是 **Windows 版**  
（`electron.exe`、`.dll`、`path.txt` 内容为 `electron.exe`），所以  
`node src/cli.js`（纯 Node）能跑，但 `electron .`（GUI）在 Linux 上直接失败。

**处理**：重新下载 Linux x64 的 `electron-v31.7.7-linux-x64.zip`  
（`https://npmmirror.com/mirrors/electron/31.7.7/`，约 101 MB），解压替换  
`node_modules/electron/dist/`，并把 `path.txt` 改为 `electron`。

**两个小坑**：

1. `path.txt` 用 `echo electron > path.txt` 会**多一个换行**，Electron 启动报  
   `spawn .../electron\n ENOENT`。必须用 `printf 'electron' > path.txt`。
2. `.bin/electron` 来自上传的压缩包，**没有执行权限**，报  
   `env: './node_modules/.bin/electron': Permission denied`。需要 `chmod +x`。

### 5.2 Linux 工作站在 Wayland 下：GUI 需要手动指定 DISPLAY / XAUTHORITY  

该 Linux 工作站是纯 Wayland（GNOME 50，无 Xorg 会话）。nut-js 走 Xwayland 注入是可行的，  
但进程环境里没有正确的 `DISPLAY` / `XAUTHORITY`。

**处理**：Linux 启动脚本从 `gnome-shell` / `Xwayland` 进程的 `/proc/<pid>/environ`  
里探测出 `DISPLAY` 和 `XAUTHORITY`。  
GUI 启动还要额外加 `--no-sandbox`（否则 chrome-sandbox 权限报错）。

实测确认：注入可用（能读取屏幕几何并移动光标）。  

### 5.3 控制权 enter/release 死循环（刷屏 `returning control`）

**现象**：client 端日志每秒刷几十条 `returning control to server`，功能不可用。

**根因**：进入远程控制的**瞬间**，光标就被注入到共享边缘位置，于是两侧的  
「触边判定」立即为真，互相触发：

- server 端 `release` 后，物理光标仍被 `pinCursor` 钉在边缘，下一帧又 `enter`；
- client 端一进门光标就在 home 边缘，立刻 `release`。

形成 `enter/release` 死循环。

**修法**（两处对称的「先离边、再触边」门槛）：

- `src/app.js` 的 client `watchCursor`：加 `armed` 标志，光标必须先离开边缘  
  8px（`LEAVE`）进入屏幕内部，之后再次触边（`EDGE=2px`）才算「回家」。
- `src/server-input.js` 的 `onMouseMove`：加 `armed` 标志，`release()` 时置  
  `armed=false`，光标必须先内移 6px（`PULLBACK`）才允许再次捕获。

加了回归测试（`selftest.js`）固化这个行为。

### 5.4 真正让功能「不生效」的根因：多屏坐标系不一致

门槛修好后仍不生效。用一个临时 TCP 探针连上 server、打印它实际推送的  
`mm` 坐标，发现 **x 大量为负数**（如 `-302`、`-47`、`-2`）。

**查明**：server（Windows）的虚拟桌面是双屏水平拼接，而 `config.json` 里的  
兜底尺寸与实际布局不一致。且 uiohook 报告的是  
**虚拟桌面绝对坐标**，多屏时原点可能为负，旧代码按「单屏尺寸」硬编码归一化，  
所以：

- client 用错误的 `srcW` 换算 → 坐标溢出/错位 → 光标卡在边缘或乱跳；
- 多屏拼接/负原点场景下边缘判定也错。

**修法**（核心）：让 server 端**自动检测虚拟桌面**，坐标以桌面为基准：

| 文件                               | 改动                                                                                                                                                                                              |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/platform.js`                | 新增 `detectVirtualScreen()`（Win: PowerShell `SystemInformation.VirtualScreen`；Linux: 解析 `xrandr`）和 `detectMonitors()`（每块屏的 bounds，primary 优先）；新增 `parseXrandrBounds()` / `parseXrandrMonitors()` |
| `src/server-input.js`            | 用虚拟桌面原点 `(VX,VY)` 把 uiohook 绝对坐标换算成桌面内相对坐标再发送；`enter` 消息带上 `vw/vh`；边缘判定按「触发矩形」计算，并加「垂直方向也在该屏范围内」的门槛                                                                                             |
| `src/client-input.js`            | 用 `enter` 消息里的 `vw/vh` 作为缩放源尺寸（config 只作旧版兜底），不再依赖手填值                                                                                                                                           |
| `src/config.js`                  | `layout` 新增 `monitor` 字段（`all` / `primary` / `0` / `1` …），默认 `all`                                                                                                                              |
| `src/ui/*`                       | 分辨率字段改称「服务器虚拟桌面」，新增「触发边缘的显示器」下拉 + 「检测本机多屏布局」按钮（走新增的 `app:getMonitors` IPC）                                                                                                                      |
| `src/preload.js` / `src/main.js` | 新增 `getMonitors` 桥与 `app:getMonitors` 处理器                                                                                                                                                       |

### 5.5 多屏选项（`layout.monitor`）

默认 `all` = 整个虚拟桌面（`edge=right` 即整个桌面的最右边）。  
多屏时若对端在左侧，应选**具体那块屏**（如 `0`），程序取该屏的边界做触发矩形，  
`edge=left` 就是那块屏的左边缘。`detectMonitors()` 按 primary 优先排序，  
所以 `0` 通常是主屏。

### 5.6 验证

- `node src/selftest.js`：96 键映射 + 边缘门槛回归 + **多屏解析回归**  
  （含负原点 `1920x1080-1920+0`）。
- 真机 xrandr 解析：`detectVirtualScreen()` 正确返回桌面几何，  
  `detectMonitors()` → 单屏正确。
- client 连上 server 正常，不再刷 `returning control`。

**未完成**：修复只在 Linux 侧的源码里，**Windows server 那台仍是修复前的旧  
exe/源码**，需要在 Windows 上重新打包（或直接跑新源码）才能让多屏修复生效。

### 5.7 架构隐患（尚未处理）

1. **server 端不拦截本地事件**。`pinCursor` 只是把光标挪回边缘，并不吞掉事件，  
   远程操作期间物理点击仍可能落到 server 本地窗口。要彻底解决需引入真正的  
   输入拦截层（X11 grab / Windows LL hook 吞事件）。
2. **VM 当 server 语义不对**。物理鼠标在宿主机上，VM 内的钩子看到的是 VM  
   自己的坐标，和「跨设备」语义冲突。真实部署应为「物理 Windows 作 server +  
   Linux 工作站/另一台作 client」。  
3. **Wayland 下该 Linux 工作站作 server 不可行**（无全局输入捕获），只能作 client。

### 6.1 合并 v1 → 主项目

v1 是完整的 Linux 工作副本（`node_modules/electron/dist` 里是 **Linux 版** Electron，  
`path.txt` 内容为 `electron`），带着阶段五的多屏修复。把 `src/*`、`config.json`、

（这样本机可以直接打 Windows 包）。

### 6.2 v1 里发现的三个真实缺陷（本阶段修掉）

审读 v1 代码时发现的、静态检查看不出来的问题：

1. **检测结果永久缓存**。`detectVirtualScreen()` / `detectMonitors()` 用模块级变量缓存，  
   没有失效入口。后果：多屏热插拔、改分辨率后**必须重启程序**才生效；  
   界面上的"检测"按钮也会返回旧值。
2. **高 DPI 下坐标偏差**。`powershell.exe` **不是** per-monitor DPI aware，  
   它的 `Screen.Bounds` 返回的是**虚拟化后的逻辑像素**；而 uiohook 报告的是**物理像素**。  
   在缩放屏（如 150%）上两者对不上 → 边缘判定偏移。
3. **`layout.monitor` 用索引存**。显示器增减/换顺序后索引指向错误的屏。

**修法**

| 文件                              | 改动                                                                                                                                                                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `src/platform.js`               | 重写。优先用 **Electron `screen` 模块**（DPI 感知、物理像素、无子进程）取每块屏 bounds，回退 PowerShell/xrandr；`getScreenInfo()` 一次返回 `virtual + monitors + signature`；`invalidateScreenCache()`；`resolveMonitor()` 支持 `all`/`primary`/索引/**几何签名**；`monitorSig()` |
| `src/server-input.js`           | 几何可**热刷新**（Electron 下 3s、headless 30s 轮询），布局变化时重算触发矩形并**重发 `enter` vw/vh**；显示器解析走 `resolveMonitor`                                                                                                                                   |
| `src/client-input.js`           | 客户端也按**本机虚拟桌面**换算注入坐标（原来用 nut-js 的主屏尺寸），支持负原点；每次 `enter` 重新检测本机布局                                                                                                                                                                    |
| `src/app.js`                    | client 的 home 边缘判定改用**本机虚拟桌面**边界                                                                                                                                                                                                     |
| `src/config.js` / `config.json` | 新增 `input` 与 `clipboard` 配置段                                                                                                                                                                                                         |

### 6.3 真·输入拦截（应用层方案）

**结论先行**：本机**没有任何 C/C++ 编译器**（gcc/clang/cl 全无），且**安全策略禁止  
`Add-Type` 动态编译 .NET**。所以"内核级吞事件"（`WH_MOUSE_LL` 回调返回非零）这条路  
在本仓库不可行——需要原生编译产物。

**采用的方案**：`src/blocker.js` —— 一层**覆盖整个虚拟桌面的无边框、透明、置顶窗口**  
（`setAlwaysOnTop(true, "screen-saver")`）。它是最顶层窗口，指针输入落在它身上并被丢弃，  
不会传给用户原本在用的程序；键盘焦点尽力争取（Windows 的 `SetForegroundWindow` 有  
前台进程限制，但遮罩一旦被点到就会拿到焦点）。真实事件仍由全局 uiohook 捕获转发，**不丢**。

**过程中撞到的两个真坑**

1. **构造函数的 bounds 被工作区裁剪**。`new BrowserWindow({ x, y, width, height })` 会被  
   任务栏挤掉高度：实测 1280×800 的桌面只得到 **1280×752**。必须在窗口就绪后  
   再 `setBounds(desktopBounds())` 覆盖一次，才真正铺满。
2. **销毁遮罩会退出整个应用**。遮罩窗 `destroy()` 后若成为"最后一个窗口"，会触发  
   Electron 默认的 `window-all-closed` → 应用退出。改为 **`hide()`**（只隐藏、不销毁，  
   退出时才 destroy），既避开该边界，又省掉反复重建。

**逃生热键**：`src/hotkey.js` 把 `"Ctrl+Alt+Shift+Q"` 解析成"每组至少按下一个"的键码组  
（左/右 Ctrl、Alt、Shift 都接受），由 uiohook 全局读取，**不受焦点影响**；  
命中即 `release()` 并解除遮罩。托盘菜单与设置窗口也各有一个「交还本地控制」。

### 6.4 剪贴板共享

`src/clipboard.js`：两端各自轮询本地剪贴板，变化则发 `{ t: "cb", text }`；  
收到后写入本地并记住该值，**抑制回声**（否则两端会来回弹）。只在连接建立期间运行，  
上限 1 MB。`io` 与 `send` 注入，便于单测。

### 6.5 重连加固

发现一个真实 bug：`connectClient.close()` 清了重连定时器，但 `socket.destroy()` 触发的  
`close` 事件**又排了一个新的重连**——即"停止节点后仍会重连"。改为 `stopped` 标志 +  
**指数退避**（1s→2s→4s→8s→15s，带抖动），连接成功时重置计数。

## 7. 阶段七：对打包源码做端到端验证与修复（2026-10-10 晚）

### 7.1 约束与思路

本机只有 Windows，**没有第二台 Linux 机器**，做不了真实双机联调。  
所以这一阶段的目标不是「跑一次看行不行」，而是：

1. 把「能不能互联移动」拆成**可判定的断言**，用**真代码 + 真 socket** 跑一遍完整闭环；
2. 把只有 Linux 才能验的部分（X11 钩子、注入、依赖库）变成用户在**自己机器上一条命令就能查**的自检。

为此加了两样东西（都留在仓库里）：

| 文件                                                            | 作用                                                                     |
| ------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `test/e2e.js` + `test/node-runner.js` + `test/mock-native.js` | 端到端回环测试：真 server 角色 + 真 client 角色，**两个独立进程**，走**真实 TCP**，只把原生输入层换成可控替身 |
| `src/doctor.js`                                               | 体检脚本：在任意一台机器上跑，逐项检查能不能当 server / client，缺什么直接给 apt 命令                  |

替身只替换两件事：`uiohook-napi`（事件来源）和 `@nut-tree-fork/nut-js`（注入去向）。  
**协议、边缘判定、相对位移、注入换算、返回判定用的都是仓库里的真代码。**  
替身里的指针模型是「物理光标」：手动位移会移动它并被**桌面边界夹住**（和 Windows 一样），  
而 `setPosition` 是瞬移（server 自我回中就是这么做的）。

### 7.2 先跑基线：一口气暴露 4 个问题

第一次 `node test/e2e.js`，18 项里挂了 4 项。逐条定位后确认是 **3 个真 bug + 1 个测试自身的问题**。

#### 真 bug A：右 / 下边缘会在屏幕中间就触发

阶段六那版 server 用「从光标自己身上学桌面范围」（envelope：记录光标走过的 min/max）判右边和底边。  
这个思路**自指**：`maxX` 永远等于光标当前所在位置，于是「光标到达右边缘」的条件  
`e.x >= box.x + box.width - 1` 实际等价于 `e.x >= maxX - 1`，**在光标每次刷新最右点时都成立**。

实测：从 x=300 一路向右扫，**扫到 x≈700（1920 屏的中间）就切走了**。

**修法**：边缘判定**只用系统几何**（Electron `screen` / xrandr，都是物理像素，与钩子同一坐标空间），  
只有系统几何拿不到时才退回 config 的 `screenWidth/Height`。  
envelope 保留，但**只用于诊断**：光标扫过大部分桌面后，若钩子观测尺寸与系统几何差 >10%，  
打 warning 提示 DPI / 多屏设置可能不对。

#### 真 bug B：滚轮永远向上

`uiohook` 的 `wheel.direction` 是**轴**（`3`=竖直 / `4`=水平），不是方向；  
方向在 `rotation` 的**正负**里。client 却写成 `if (msg.d >= 0) scrollUp`，  
而 `d` 永远是 3 或 4 → **任何滚动都被当成向上**。

**修法**：用 `rotation` 正负判上下，并补上水平滚轮（`scrollLeft` / `scrollRight`）。

#### 真 bug C：client 光标永远到不了自己的边缘（会卡在远程）

这条最能解释「鼠标不能互联移动」。原设计在捕获瞬间把 server 物理光标**只回中一次**，  
之后靠相邻两次钩子采样的差值转发位移。

问题在于 **Windows 会把光标夹在屏幕边界**：回中到 x=800 后，往左最多只能再走 800px 就没事件了。  
而 client 光标要从自己桌面中心走到「回家边」，需要跨**半个屏**（2560 屏要 1280px）。  
`800 < 1280` → client 光标停在半路 → **永远触发不了返回，卡在远程**，只能按逃生热键。

**修法**：加「死区回中」。捕获期间只要物理光标靠近桌面任意边界 120px 以内，就瞬移回桌面中心；  
瞬移产生的巨大跳变（>400px）用阈值识别，**不当成手部位移转发**。  
这样 server 光标永远有充足行程，client 光标能走完整屏。

> 阈值 400px 的依据：100Hz 采样下，人手两次采样间不可能移动 400px（=40000px/s）。


#### 测试自身的问题

「松手后停在边缘不应立刻重新捕获」这条一开始也挂了，但**不是产品 bug**：  
这个设计里 client 要「回家」必须往**背离**共享边的方向移动，  
所以 client 松手时 server 光标一定**不在**共享边上，那个状态不可达。  
改成更有意义的断言：**松手后无输入时不得抖动**（不许出现 capture/release 循环）。

### 7.3 顺手修的两处问题

**a. client 记录的光标位置没加桌面原点。**  
`getTrackedPosition`（返回判定用它）原来返回的是相对 (0,0) 的值，  
多屏、主屏不在 (0,0) 的机器上会和 `getLocalBox()` 对不上。  
现在统一成**绝对桌面坐标**（含原点），种子点、夹取范围、返回判定三者一致。

**b. client 必须手填和 server 一样的 `edge`，填错就回不来。**  
这是配置层面的坑：`homeEdge` 原来是 `oppositeOf(自己 config 的 edge)`，  
两端 `edge` 不一致（很常见，客户端那台往往忘了改）就会在错误的边上找"回家"。  
现在 server 在 `enter` 消息里带上 `edge`，client **直接采用 server 的**，  
自己 config 的值只作为旧版本对端的兜底。

> 测试里把 client 的 `edge` **故意设成相反值**来验证这条：18/18 仍然通过。

## 8. 阶段八：混合 DPI、本机自检、按键与滚轮、平台拆分、Wayland 后端（0.2.1 → 0.2.7）

用户反馈三条，按时间顺序：① 双屏 Windows 混合缩放环境下往左推 Ubuntu 不动；
② 鼠标能移动但左键和滚轮失效。三条都在本阶段定位并修掉。

### 8.1 混合 DPI 下 DIP → 物理像素换算是错的

**现象**：单屏 / 相同缩放时一切正常，混合缩放时共享边落到了屏幕内部。

**根因**：`Display.bounds` 是 **DIP**，`uiohook` 报的是 **物理像素**，而代码用
`bounds * scaleFactor` 做换算。这在「所有屏幕同一缩放」时碰巧成立，
混合缩放时错得很厉害 —— 因为 Chromium 的 DIP 布局是一棵**以主屏为根的树**，
子屏的 DIP 原点是**父屏的 DIP 边缘**，不是 `自己的物理原点 / 自己的 scaleFactor`。

测试机器（副屏在**右**）：

| 项目 | DIP / 朴素换算 | 实际物理布局 |
| --- | --- | --- |
| 副屏原点 | 按缩放比例推算 | 由系统几何接口检测 |
| 虚拟桌面边界 | 由显示器 DIP bounds 推算 | 由系统几何接口检测 |

差 1080px，于是共享边算出来落在副屏内部，永远推不到。

**解法**：改用 Electron 官方给的权威换算 `screen.dipToScreenRect(null, rect)`
（文档明确：窗口为 null 时「按距离最近的显示器换算」），
失败才退回 `bounds * scaleFactor`。同时区分开两个函数：

* `detectVirtualScreen()` —— 物理像素，给**钩子**和边缘判定用；
* `detectVirtualDipScreen()` —— DIP，给 **`BrowserWindow.setBounds()`** 用。

> 顺带修掉第二个同源 bug：输入遮罩窗把**物理**像素喂给了 `setBounds()`
> （它要的是 DIP），200% 屏上遮罩大一倍且位置错。

**可诊断**：启动日志逐屏打印几何与共享边归属，例如
`共享边 left 属于显示器 #1（非主屏）；注意：该边不在主屏上…`；
托盘菜单可一键切换共享边，并新增 `edge: "any"`（碰哪条边都交出去）。
新增 `--diag` 诊断报告，逐屏并排打印三种换算结果。

### 8.2 本机自检 `--hwtest`：一台机器就能判定是哪一侧坏了

**问题**：「推过去没反应」这句话本身是**歧义**的 —— 分不清是
server 侧坏了、client 侧坏了、还是网络坏了。而所有既有测试都把原生层换成了替身，
对真实硬件一句话都证明不了。

**做法**：`src/hwtest.js`，用**真实全局钩子 + 真实光标 + 真实 TCP 回环**
（监听 `127.0.0.1` 再连自己），把光标依次推到四条边，逐条检查：
光标能否到达该边 → 边缘判定是否在 0px 处触发 → 对端是否收到 `enter`
→ `release` 是否交还控制。跑完把光标放回原位。

```bash
NetMouse.exe --hwtest              # 四条边，约 10 秒
NetMouse.exe --hwtest --edge left  # 只测一条边
```

判定逻辑：**四条边全触发** → 本机 server 侧没问题，去查 client 或网络；
**只有部分触发** → 把共享边改成能触发的那条；**一条都不触发** →
就不是「配错边」，是几何或钩子本身的问题。

**写这个自检时自己踩了三个坑**（每一个都会让自检**说谎**，值得记下来）：

1. 没调 `setEdge`，server 一直盯着 `layout.edge`（=right），另外三条边永远不触发。
   —— 这**恰好复现了用户的原始症状**，反过来证明「配错边」确实会让往左推毫无反应。
2. 传了 `onPeer` 但没注册 `peer.onMessage`，对端的 `release` 被静默丢弃。
3. 把 server 要发的消息写到了**对端**的 socket 上（方向反了）。
   阴险之处在于那个 socket 是活的（`destroyed=false writable=true`），
   一切看起来都正常，数据却在往回走。最后靠 30 行独立探针才找到。

### 8.3 按键失效：`Button.LEFT === 0` 是假值

**现象**：鼠标能移动，但**左键点了没反应**（右键、中键正常），滚轮也不对。

**根因**：两套按键编号不一样，而代码用**真值判断**做了桥接：

| | 左 | 中 | 右 |
| --- | --- | --- | --- |
| uiohook（`MOUSE_BUTTON1..3`） | 1 | 3 | 2 |
| nut-js（`Button` 枚举） | **0** | 1 | 2 |

```js
const BTN = { 1: Button.LEFT /* = 0 */, 2: Button.RIGHT, 3: Button.MIDDLE };
...
if (b) await mouse.pressButton(b);   // ← Button.LEFT 是 0，`if (0)` 为假
```

于是**左键被整个丢掉**，而右键（2）、中键（1）都是真值所以正常。
移动走的是另一条路径，完全不受影响 —— 症状正好是「能移动，点不动」。

**解法**：`buttonFor()` 显式返回 `null` 表示「nut-js 注入不了」，
调用处一律用 `b !== null` 判断，**绝不用真值判断**。
侧键 4/5（后退/前进）nut-js 没有对应枚举，记录一次日志后忽略，不再静默丢弃。

**为什么之前的测试没抓到**：`test/mock-native.js` 里的替身把
`Button` 写成了 `{ LEFT: 1, RIGHT: 2, MIDDLE: 3 }`（那是 **uiohook** 的编号，
不是 nut-js 的）。替身里 `Button.LEFT = 1` 是真值，所以测试通过；
真库里 `Button.LEFT = 0` 是假值，所以线上丢事件。**替身必须能像真库一样失败。**

### 8.4 滚轮：rotation 的含义、符号与单位

三个独立的错误叠在一起：

1. **`rotation` 是「格数」，不是 ±120。** libuiohook 在
   `input_helper.c` 里做了 `value = v_rotation / -120` 的归一化。
   旧代码写 `Math.round(Math.abs(r) / 120)`，恒等于 0，再 `Math.max(1, ...)` 恒等于 1。
2. **符号反了。** libuiohook 各平台统一约定
   （X11 `WheelUp/WheelLeft = -1`，Windows/macOS 的写法与之对齐）：
   `rotation < 0` = 上/左，`rotation > 0` = 下/右。
   旧代码把 `>= 0` 当成向上，于是**上下颠倒**。
3. **`rotation === 0` 不是滚动。** 高精度触摸板 / 惯性滚轮会产生**不足一格**的增量，
   libuiohook 把余数累积起来、不够一格就报 0。旧代码把 0 归进
   「`>= 0` 所以向上」，于是每来一个微小增量就往上滚一下。

另外还有一个**跨平台陷阱**：nut-js 的滚轮 `amount` 含义不统一
（`libnut-mouse.class.js` 把它原样转发给 libnut）：

| 平台 | `amount` 的含义 | 一格 = |
| --- | --- | --- |
| Windows | `MOUSEEVENTF_WHEEL` 的原始 delta | **120** |
| X11 | 点击次数（每次按一下 button 4/5） | 1 |
| macOS | `kCGScrollEventUnitLine` 的行数 | 1 |

**在本机用真实钩子实测确认**：`scrollUp(120)` → rotation `-1`（正好一格）、
`scrollUp(240)` → `-2`、`scrollUp(1)` → `0`（1/120 格，等于什么都没做）。
所以「传 1 格给 nut-js」在 Windows 上滚**零**，在 Linux 上滚一格。
新增 `platform.scrollUnit()`（win32 → 120，其余 → 1），
并留了 `input.scrollUnit` 配置项兜底（0 = 按平台自动）。

**解法**：`wheelAction(rotation, direction, unit)` 纯函数：
`rotation` 为 0 → 返回 `null`（不产生任何注入）；否则取符号定方向、取绝对值定格数、
按 `unit` 换算，并夹到 20 格上限。server 侧也顺手在 `onWheel` 里把 0 直接丢掉，
不再占用带宽。

### 8.5 顺带修掉的：跨边界拖拽会留下「粘住的按键」

如果用户按着左键从 server 拖到 client，再在 server 上松手，
这个 `mouseup` 是 server 的钩子收到的，**永远不会转发给 client**，
于是对端那个按键**一直按着**（表现为拖拽/框选停不下来）。
新增：client 在交还控制前（以及连接断开时）调用 `releaseAll()`，
把自己按下的键全部松开。

### 8.7 界面里把「Windows / Linux 的差异」拆成可见的选项（0.2.4）

**起因**：用户问「Win11 和 Ubuntu 的模式是不是不一样，能不能在软件里把选项拆开」。
这问得对 —— 前面几轮踩的坑（滚轮一格是 120 还是 1、要不要 `--no-sandbox`、
几何从哪来、遮罩怎么置顶）**全都是平台差异**，但界面上完全看不出来，
用户只能靠读 README 去猜「我这台该填什么」。

**做法**：不新增「模式」开关（多一个开关就多一种组合，反而更容易配错），
而是把**平台差异本身**做成信息，并让**能自动判断的都自动判断**：

1. **本机平台卡片**（`#cardPlatform`）：顶部一颗 OS 药丸显示本机平台（如 `Windows x64`），
   下面按平台分块列出 `geometry / scaling / injection / wheelUnit / sandbox / deps / tray`
   七项事实。数据来自 `platform.js` 新增的 `platformInfo().facts`，
   **界面不硬编码任何平台知识** —— 以后加平台只改一处。
2. **本机 / 非本机区分**：非本机那一块加 `.osblock--other` 半透明 + 角标
   「（非本机，仅供参考）」，避免用户照着另一台平台的说明去填本机配置。
   还有一个 `#onlyLocal` 复选框（持久化在 `localStorage["netmouse.onlyLocal"]`）
   可以把非本机块整块折叠掉。
3. **差异对照表**（`#cardDiff` → `#diffTable`）：8 行并排对比 Windows 与 Linux，
   本机那一列高亮（`.diffcell--local`）。8 行是：
   屏幕几何来源 / 缩放·高DPI / 输入注入方式 / 滚轮一格单位 / 额外运行时依赖 /
   沙箱 / 会话类型 / 系统托盘。
4. **作用域标签**：每个卡片标题旁挂 `仅服务器` / `仅客户端` / `两端都要`
   小标签（`.scope`），因为「共享边」只有 server 有意义、
   「滚轮单位」只有 client 有意义 —— 之前用户经常在错的那台上改。
5. **滚轮单位提示**（`#scrollUnitHint`）：把「0 = 按平台自动」展开成
   「本机（Windows）自动值是 120」，用户一看就知道该不该动这个值。

**为什么用「事实」而不是「模式」**：模式是**用户要记的东西**，
事实是**程序已经知道的东西**。既然 `process.platform` 一定能告诉我们是哪台，
就不该让用户去选。

**新增静态校验** `test/ui-check.js`（不依赖 Electron，纯文本解析）：
逐个断言 `renderer.js` 里出现的每个 `$("id")` 在 `index.html` 里**真的存在**、
新增的平台元素都在、`renderer.js` 里确实有 `renderPlatform` / `applyPlatformFilter` /
`renderScrollUnitHint`、`collect()` 真的会把 `scrollUnit` 发出去、
`fillForm()` 真的会把它读回来、以及每个新 CSS 类都在 `style.css` 里有定义。
界面改坏了会在 `npm test` 里立刻红掉，而不是等用户点开界面才发现。

**离屏渲染实测**（临时 Electron 脚本 + stub preload + `capturePage()`）：
`osPill: "Windows x64"`、`platRows: 6`、`diffRows: 9`（表头 + 8 行）、
`diffNotes: 8`、`localCells: 8`、`scopeChips: 5`、
`scrollHint: "0 = 按平台自动。本机（Windows）自动值是 120…"`，
勾上 `onlyLocal` 后 `linuxHidden: true`。
截图留在 `reports/示例-设置界面-平台拆分.png`（`reports/` 随源码包一起分发，
见 [`../reports/README.md`](../reports/README.md)；里面的 `示例-*.txt`
是 0.2.7 实跑出来的报告原文，可直接对照格式）。

> ① `localStorage` 是按 userData 目录持久化的，反复截图会读到上一次的筛选状态，
> 得用一次性的 `app.setPath("userData", mkdtempSync(...))`；

> 所以「对照表是不是 8 行」最后是靠 `executeJavaScript` 把 `#diffTable` 的文本 dump 出来数的。

### 8.8 「Ubuntu 上鼠标不动」：日志在说谎，因为注入失败被吞掉了（0.2.5）

**用户报告**：两台 Win11 之间已经正常；Win11 ↔ Ubuntu 时**鼠标不动、点击也失效**，
附上了 Windows 侧 `diag` 报告和 Ubuntu 侧的运行日志。

**先看日志能证明什么。** Ubuntu 客户端的日志里有这样一段：

```
<time> local desktop detected: <detected-size> [electron]
<time> returning control to server
```

这两行都是**有确切含义的**，把它们读对，结论就出来了一半：

* `local desktop detected` 只在 `ensureSize()` 里打印，而 `ensureSize()` 只在
  客户端刚构造时和**收到 `enter` 时**（`handle("enter")` 会清掉 `dst`）被调用。
  所以它出现 = **服务器确实捕获了，`enter` 也确实到了**。
* `returning control to server` 只在 `watchCursor()` 里 `dist <= EDGE` 时打印，
  而 `dist` 是从 **`inject.getTrackedPosition()`** 算的 —— 那是我们**自己累加**的位置，
  从桌面中心播种、每收到一个 `mm` 就前进，**不是把真实光标读回来的**。

于是：`mm` 消息确实到了、确实被处理了、累计位置确实从中心（1280,720）一路走到了
`x <= 2`（否则根本不会触发回家判定）。**而这一切和「注入有没有落到操作系统上」完全无关。**

再看代码里那一行：

```js
mouse.setPosition(new Point(x, y)).catch(() => {});   // ← 每一次注入失败都被吞掉
```

所以日志**不可能**区分「一切正常」和「这台机器一次注入都没成功」。
结合「两台 Win11 之间是好的」（同一套协议、同一个服务器端，所以协议和 server 侧没问题），
故障被定位到 **Ubuntu 客户端的注入**。日志里没有一条错误，恰恰是因为错误被吞了。

**根因（代码层面）**：`client-input.js` 用 `.catch(() => {})` 结尾，
`flushMotion` 里那一行尤其致命 —— 它让「注入全挂」和「注入全好」在日志里长得一模一样。

**这次不是猜，是把「猜不出来」这件事本身修掉。**

### 8.8.1 客户端侧自检 `--injecttest`（新增 `src/injecttest.js`）

`--hwtest` 检验的是**服务器侧**（几何、边缘判定、交接），而且在客户端上会**直接拒绝运行**
（「本机自检只对服务器端有意义」）—— 于是客户端这一半**从来就没有过测试**，
而「对端鼠标不动」恰恰是个客户端问题。

新的自检**驱动真正的客户端注入器**（就是 `createInjector()`，客户端的原班代码路径），
喂它真正的协议消息，同时用**真正的全局钩子**看操作系统到底收到了什么：

| 喂进去 | 断言 |
| --- | --- |
| `enter` + 6 × `mm` | 真实光标有没有跟着我们驱动的目标走 |
| `md`/`mu` × 左/右/中 | 钩子有没有看到 button 1/2/3 按下与松开 |
| `wh` × −1/+1 | 钩子有没有看到一格滚轮，方向对不对 |

三项**各自独立下结论**，因为它们是三条独立代码路径，
而「就是不行」在知道是哪一条之前是没法修的。

入口：`NetMouse --injecttest` / `npm run injecttest` / 托盘菜单 / 设置界面「本机注入自检」按钮。

### 8.8.2 注入失败不再静默

`client-input.js` 现在记录 `applied` / `errors` / `lastError`，失败时**只报一次**
（不然一次远程控制能刷出几千行），并带上真实错误文本和下一步该跑什么。
`app.js` 的客户端在**交还控制时**比对本次会话的失败数：有失败就报「本次远程控制期间有
N 次注入失败」，而不是照常打印那句让人误以为成功的 `returning control to server`。

> 这里有个容易做错的地方：`getTrackedPosition()` 是纯算术，**注入全挂时它照样走到边缘**，
> 所以「能回家」这件事**不能**当成「注入成功了」的证据。判据必须是注入器自己的计数。

顺带：`platformInfo().warnings`（Wayland / 缺 DISPLAY / 缺 xdotool）以前**只在界面上显示**，
headless 运行或用户发过来的日志里根本看不到 —— 现在两端 `start()` 都会把它们写进日志。

### 8.9 真凶是 Wayland：XTest「成功但没人收到」（0.2.6）

用户报告：**两台 Win11 之间正常，Win11 ↔ Ubuntu 之间鼠标不动、点击无效**，
并附上了**两端**的诊断日志。

#### 先把日志读对：协议层完全正常

两端日志的本地时区不同，对齐之后是**一一对应**的：

| Windows（server）           | Ubuntu（client）                 |
| ------------------------- | ------------------------------ |
| `16:23:57 captured -> forwarding` | `01:23:57 local desktop detected` |
| `16:24:05 released -> local control` | `01:24:05 returning control to server` |
| `16:25:52 captured`       | `01:25:52 local desktop detected` |
| `16:25:57 released`       | `01:25:58 returning control to server` |

`local desktop detected` **只在收到 `enter` 时**打印，`returning control` 依据的是
客户端自己累加的位置 —— 两者都说明 `enter` / `mm` / `release` **一路都到了、都被处理了**。
再叠加 server 侧 `--hwtest` 的四条边全触发 + 按键滚轮 6 项全过，
**故障点被锁死在「Ubuntu 客户端的注入」这一环**。

#### 真凶：Wayland

Ubuntu 的日志第 166 行自己就写着：

```
01:22:57环境: Wayland 会话，当前通过 Xwayland 工作（DISPLAY=:0）。功能可能不完整。
```

而**注入侧一条错误都没有**。这两件事合起来才是关键：

* Xwayland **实现了 XTest 扩展**，所以 `XTestFakeMotionEvent` 等调用**全部返回成功** ——
  libnut 不抛异常，promise 不 reject，`.catch` 永远不会触发。
* 但 Xwayland 只是合成器的一个客户端。它合成出来的事件**只送给 X11（Xwayland）客户端**，
  原生 Wayland 应用收不到；**指针 warp 也不会被合成器采纳**，真实光标一动不动。

于是「注入全挂」和「注入全好」在日志里**长得一模一样** —— 和 8.8 是同一类病，
只是这一次连「调用失败」都没有，比 8.8 更隐蔽。

> 这正是本项目反复踩的同一个坑的第三形态：
> ① 左键被真值判断丢掉（`Button.LEFT === 0`）；② 注入失败被 `.catch(() => {})` 吞掉；
> ③ **注入调用成功，但事件在显示服务器层面被丢弃**。前两个是代码问题，这个是**架构问题**。

#### 解法：绕过显示服务器，走内核 uinput

唯一能在 Wayland 下注入的方式是**在显示服务器下面**动手：通过内核 `uinput` 模块
创建一个虚拟输入设备，合成器就会把它当成一只真鼠标、一个真键盘 ——
Wayland、X11、甚至纯文本终端都能用，因为压根不经过显示服务器。

建这个设备需要对 `/dev/uinput` 做 `ioctl()`，Node 做不了（本项目坚持只发 N-API 预编译包，
不带编译器），所以**驱动现成的 uinput 工具**，走行协议：

| 工具        | 传输                        | 移动 | 按键 | 滚轮    | 键盘 | 说明 |
| --------- | ------------------------- | -- | -- | ----- | -- | -- |
| `dotool`  | 常驻进程，stdin 逐行喂           | ✓  | ✓  | **✓** | ✓  | **首选**，唯一支持滚轮 |
| `ydotool` | 每次动作 fork 一个进程（靠 ydotoold） | ✓  | ✓  | **✗** | ✓  | 兜底；无滚轮，移动限流 ~60Hz |

* 新增 `src/inject-uinput.js`：动作 → 命令行的两个**纯函数**（`dotoolLine` / `ydotoolArgs`）、
  能力表、工具探测、以及一个 `spawn` 可注入的传输层（单元测试用假 child 断言**确切字节**）。
* `input.backend = auto | xtest | uinput`。**默认 auto**：X11 用 XTest，
  Wayland 且装了 uinput 工具就自动切过去。会话类型程序自己能看出来，
  不该让用户去回答一个程序已经知道答案的问题。
* **按键不需要任何映射表**：`uiohook` 的键码**就是**内核的 `KEY_*` 码
  （`VC_A = KEY_A = 30`，字母数字区整段都成立），所以 server 现在在 `kd`/`ku` 里
  多带一个 `k` 字段（原始 uiohook 键码），客户端直接发 `keydown k:30`。
  旧的 `c`（nut-js Key）保留给 XTest 路径，老对端忽略新字段即可。
* 滚轮符号：libuiohook 用 `rotation < 0 = 上`，而内核 `REL_WHEEL +1 = 上`，
  两个约定只在 `uinputWheelAmount()` 一处交汇 —— 单独成函数并写了注释，
  因为这种反向一旦搞错，症状就是「滚轮方向反了」。

#### 顺手修掉的两处「会说谎」的地方

1. **`--injecttest` 在 Wayland + XTest 下不再给结论**。这是个真陷阱：
   自检用全局钩子看结果，而 Xwayland 会把我们注入的事件**原样回放**给钩子，
   于是「光标移动 ✓ / 按键 ✓ / 滚轮 ✓」可以全绿而实际毫无作用。
   现在检测到这个组合就直接把结论标记为**不可用**并返回退出码 1。
2. **`motionVerdict` 改成比「位移」而不是「绝对位置」**。uinput 工具只能相对移动
   （内核鼠标没有「瞬移」这种操作），真实光标必然从用户手放的地方开始，
   拿算出来的中心去比会误判。位移才是 server→client 真正承诺的东西。

#### 验证

* 新增 `test/uinput-units.js`（**37 项**）：两个工具的命令语言逐条断言；
  三套按键编号（uiohook / nut-js / 各工具自己的）对齐；
  `uiohook 键码 == 内核键码` 这个**不变量**被钉住（哪天 uiohook 改了就会红）；
  用假 `spawn` 断言常驻/逐次两种传输的确切命令行、健康计数、
  「子进程死掉只报一次、不会静默」（这条测试当场抓出了 `exitCode !== null` 时
  **不计数**的漏洞 —— 那正好又会造成「0 次失败却什么都没注入」）；
  以及 8 种后端选择组合。
* **回归纪律照旧**：把 `YDOTOOL_BUTTON` 改回 nut-js 的编号再跑，
  3 项立刻红（`buttons use the 0x40/0x80 bitmask` 等），改回即通过。
* `npm test` 现在跑**八块**：`selftest 96` · `PLATFORM 16/16` · `HWTEST-INPUT 32/32` ·
  `INJECTTEST-UNITS 19/19` · `UINPUT-UNITS 37/37` · `UI CHECK PASS` ·
  `HWTEST-UNITS 17/17` · `E2E 39/39`。
* 界面：客户端卡片新增「输入注入方式」下拉 + 实时提示（本机会选什么、为什么）。

### 8.10 让 ydotool 真的能用，以及让 Linux 也能「双击运行」（0.2.7）

这一节的两个问题都来自**真机联调**（用户提供的 `双机联调发现.md`），不是推演出来的。

#### 8.10.1 先纠正一条被写进文档的错误建议

0.2.6 的文档把「登录时选 **Ubuntu on Xorg**」列为**首选**解法。真机联调证明这条建议
在目标机器上**根本不成立**：

> 测试用 Linux 工作站：**纯 Wayland**（GNOME 50，无 Xorg 会话）。

GNOME 50 已经不再提供 Xorg 会话，登录界面上**没有那个齿轮选项**。把一条不存在的路
写成「最省事」，代价是用户去找一个找不到的菜单项。所以本轮把**顺序和语气都改了**：

* 首选改成装 uinput 工具（`sudo apt install -y ydotool`），因为这条路**永远存在**；
* Xorg 降级成「如果你的发行版还提供的话」的备选，并明确写出「GNOME 50 起多数发行版
  已不再提供」。

改动点：`platform.js` 的告警、`doctor.js` 的两条提示、`injecttest.js` 的排查顺序、
`client-input.js` 的启动告警、界面提示、便携包里的 `README-linux.txt`、README。
`platform.js` 里留了一段注释解释**为什么顺序本身是 bug 的一部分**。

#### 8.10.2 真凶之下的真凶：`ydotoold` 没跑

联调记录里那条错误信息是：

```
uinput 注入失败：ydotool mousemove -x -26 -y -557 -> exit 2
```

`exit 2` + `failed to connect socket .ydotool_socket`。原因很朴素：
**ydotool 是个纯客户端**。从 v1.0.0 起它自己什么都不做，只是往一个 unix socket 写命令，
由 `ydotoold` 守护进程持有虚拟设备并执行。守护进程没跑，每一次调用都以 `exit 2` 失败 ——
而 NetMouse 看起来就是坏的，尽管 NetMouse 没有任何问题。

联调时用户是手工救活的（`systemd-run --user --unit=ydotoold-manual /usr/bin/ydotoold`），
并在遗留项里写下：「应把『检测到 Wayland 但 ydotoold 没跑』做成启动自检并自动拉起。」
这一节就是做这件事。

**新增 `src/ydotoold.js`**，规则三条，按顺序：

1. `YDOTOOL_SOCKET` 指向一个**能连上**的 socket → 用它。这是明确的指示，不碰别的。
2. 否则探测 `$XDG_RUNTIME_DIR/.ydotool_socket`、`/tmp/.ydotool_socket`。
   **已经在跑的守护进程被复用而不是被顶掉** —— 包括 ydotool 自己的**系统服务**
   （以 root 运行，因此**完全不需要**把用户加进 `input` 组，这正是联调遗留项里
   「加入 input 组对多用户机器偏重」的答案）。
3. 都没有就自己拉起一个**私有 socket** 的实例（`.netmouse-ydotoold-<pid>.sock`），
   退出时关掉。私有是刻意的：两个 NetMouse 实例、或与用户自己的守护进程之间不会互抢。

三个决定值得单独记下来：

* **`--socket-path` 显式传，不靠环境变量。** ydotoold 的 manpage 只说 `-p/--socket-path`，
  **没有**说它读 `YDOTOOL_SOCKET`（只有客户端那页文档化了这个变量）。
  所以守护进程用 `--socket-path`，客户端用 `YDOTOOL_SOCKET`，两条路都走。
* **「socket 文件存在」≠「守护进程活着」。** 崩溃的守护进程会把 socket 文件留在原地，
  直接复用它得到的就是「每次调用 exit 2」——正是这个模块要消灭的故障。
  所以这里是**真的去 `net.connect()` 一次**（250ms 超时），连不上就自己拉一个。
* **只杀自己拉起的那个。** 复用的守护进程属于启动它的人（可能是共享的 root 服务），
  关掉 NetMouse 不该动它。测试里专门有一条断言「adopted daemon is never killed by us」。

**失败要说清楚是哪一种。** 守护进程起不来有好几种原因，症状却都是「什么都没发生」：

| 情况 | 报告 |
| --- | --- |
| 没装 ydotool | `找不到 ydotoold —— sudo apt install -y ydotool` |
| 守护进程立刻退出且 stderr 提到 `/dev/uinput` | 原文照抄 + `uinputAccess()` 给出的**确切修法** |
| 守护进程不认 `--socket-path` | `版本可能过旧（需要 ydotool ≥ 1.0）` + reinstall 命令 |
| 其它失败 | 只报原文，**不硬扯 `/dev/uinput`** |
| `manageYdotoold: false` | `自己启动：systemctl --user enable --now ydotool.service` |

最后一条是有意为之：把不相关的故障归因到 `/dev/uinput`，只会让用户白折腾一晚。
测试里有一条 `an unrelated failure does not blame /dev/uinput` 钉住这一点。

#### 8.10.3 `/dev/uinput` 的三种形态，长得一模一样

这是联调里最费时间的一段。三种完全不同的原因，症状都是「ydotoold 起不来」：

1. 用户不在 `input` 组；
2. **用户已经在组里，但当前会话还没拿到这个组** —— `usermod` 只影响之后启动的会话。
   联调时正是这一种：`usermod` 看起来成功了，设备却仍然只有 root 能写，
   于是又去跑 `setfacl` 临时救活；
3. 在组里、会话也知道，但 **udev 规则没有真的给组写权限**。

`uinputAccess()` 把三者分开报告，并且对第 2 种明确说
**「注销后重新登录即可 —— usermod 不用再跑一次」**（再跑一次是死路）。
判定方法是：读 `/etc/group` 看**应该**在哪些组里，跑 `id -nG` 看**实际**在哪些组里，
两者不一致就是第 2 种。

#### 8.10.4 Linux 上「双击就能运行」到底缺什么

用户的问题是「能否将 linux 做成像 win11 那样双击即可运行的版本」。答案是
**可以，但机制完全不同**，原因值得写下来：

* **Nautilus（GNOME 文件管理器）刻意不执行它判定为「文本」的文件**，而 `.sh` / `.run`
  正是文本 —— 双击只会打开编辑器。这是安全设计。所以「双击 `netmouse.sh`」
  在 GNOME 上**永远**不会像 Windows 那样工作。
* Linux 上「双击就能运行的程序」的**正规形式是 `.desktop` 启动器**。

所以新增 `scripts/install-linux.sh`（随便携包一起分发），跑一次即可：

```bash
./install-linux.sh                 # 应用菜单 + 桌面图标
./install-linux.sh --no-desktop    # 只在应用菜单里
sudo ./install-linux.sh --uinput   # 顺便装 /dev/uinput 的 udev 规则
./install-linux.sh --uninstall     # 删掉启动器和 udev 规则
```

它做四件事：用**绝对路径**写出 `~/.local/share/applications/NetMouse.desktop`；
拷一份到桌面；`chmod +x` 并用 `gio set metadata::trusted true` 标记受信任
（GNOME 不信任的 `.desktop` 会弹「未受信任的启动器」）；刷新 `update-desktop-database`。
脚本里同时支持从 git 检出目录运行（回退到 `run-linux.sh`）。

`package-linux-portable.py` 现在把 `install-linux.sh` 和一张 `netmouse.png`（`Icon=`
必须指向真实文件，否则菜单里是个空白图标）一起打进便携包，自解压 `.run` 首次运行时
也会提示去跑它。

**AppImage 才是「单文件、chmod +x、双击」的形态**（二进制文件，不受「不执行文本」
的限制），但 `mksquashfs` 是 Linux ELF，Windows 上打不出来 —— 命令已就绪
（`npm run build:linux:appimage`），本轮**没有构建**，如实写进待办。

### 9.1 一键诊断包（`src/diagbundle.js`）

**动机**：双机联调里最常见的一句话是「你把报告发给我看看」。但让人**手工凑一堆文件**
（配置、日志、体检、两个自检报告、平台信息）既麻烦又容易漏，而且凑出来的东西没有结构，
读的人还得逐个问「这是什么、怎么来的」。

**做法**：一个命令把该看的收进**一个 zip**，包里带一份 `README.txt` 说明每份文件是什么。

```bash
NetMouse --diagbundle              # -> netmouse-diag-<时间戳>.zip
NetMouse --diagbundle --no-live    # 跳过两个会接管光标的实时自检
```

三条设计规则：

1. **密码绝不出这台机器。** `peer.password` 被替换成 `__已隐藏__（原长 N 字符）`。
   **长度保留是有意的**：联调里「两端密码长度不一样」是常见的握手失败原因，
   光看长度就能安全地确认这件事，而不必知道密码本身。路径里的家目录折叠成 `~`。
2. **某一项失败不会让整包失败。** 每个子项（体检、自检…）跑挂时，把**失败信息本身**
   写成一个文件放进包里 —— 因为「某项跑不起来」恰恰是最该被看到的信息。
3. **不引入新依赖。** 所以 zip 是仓库里一个约 80 行的纯 Node 写包器：自己算 CRC-32、
   自己写中央目录、按需 store/deflate、名字带 UTF-8 标志（`0x0800`，因为包内文件名是中文）。

**过程中踩的两个坑，都是「清单漏了自己」**：

- `collectDiagBundle` 在 `README.txt` 被 `unshift` 进文件列表**之前**就算好了 manifest
  的文件清单，于是 manifest 永远比实际少一条。
- 反过来，README 的表格又是在 manifest 存在**之前**生成的，于是它不列 `manifest.json`。

而 manifest 的麻烦在于**它要列出自己的字节数**，可字节数取决于序列化结果，
序列化结果又取决于那个数字 —— 自指。解法是**迭代到不动点**（两次即收敛）：

```js
const entryList = () => files.map((f) => ({ name: f.name, bytes: Buffer.byteLength(String(f.data)) }));
let selfBytes = 0, manifestText = "";
for (let i = 0; i < 6; i++) {
  manifestText = JSON.stringify(buildManifest([...entryList(), { name: "manifest.json", bytes: selfBytes }]), null, 2);
  const actual = Buffer.byteLength(manifestText);
  if (actual === selfBytes) break;
  selfBytes = actual;
}
```

**验证**：`test/diagbundle-units.js`（18 项）用一个**独立的 ZIP 读回器**（不复用写包的那份
代码）反解生成的 zip —— 断言 CRC-32 向量 `0xCBF43926`、UTF-8 名称标志、store/deflate 的选择、
README 排第一、**清单把自己也列进去且字节数与真实中央目录一致**，以及那条硬规则：
**包里任何条目、任何编码下都不能出现密码明文**（含解压后的内容）。「某个收集器抛异常」
「日志对象是坏的」也各有断言 —— 它们必须变成文件，而不是让整包失败。

### 9.2 图片剪贴板（`src/clipboard.js`）

**动机**：剪贴板原来只同步纯文本，但截图互传是很自然的诉求。

**协议**：在 `hello` / `ok` 握手里加一个 `caps` 字段声明能力（目前只有 `img`）。
只有**对端也声明了 `img`** 才会推图片；对端是老版本（没有 `caps`）就自动退回纯文本。
`cb` 消息新增 `kind` 字段区分类型，**缺省即文本** —— 所以协议**字节级向后兼容**，
老版本两端照常工作。

**这里踩了一个只有真机才能发现的坑，值得完整记下来：**

Electron 的 `clipboard.readImage()` **会把位图重新编码一次**。实测：写进去一张 1×1 PNG
（70 字节），读回来的字节是 83 字节 —— 像素完全相同，编码字节不同。
如果拿**编码后的 PNG 字节**做「是不是同一张图」的去重键，两台机器就会**无限互推同一张图**：
A 发图 → B 写剪贴板 → B 轮询读到（字节变了）→ B 以为是自己没发过的新图 → 发回 A → ……

**这是纯逻辑单测抓不到的**（假后端如果直接回存原始字节，行为就和真 Electron 不一致）。
只有用真 Electron 跑一个探针才发现。

修法：去重键改成**解码后的位图**的 SHA-256（`imageKey` / `readImage().key`），
编码字节只在真的要发送时才产生。为此单测里专门造了一个 `reencodingIO` 假后端，
**模拟 Electron 的「存位图 + 重编码」行为**，并配一个守卫测试证明「这个假后端确实会改变字节，
但像素键能稳定往返」。

顺带解决的两个性能/语义问题：

- `toPNG()` 很贵（1920×1080 约 103ms，2560×1440 约 180ms），而 `toBitmap()` + SHA-256 只要 7–15ms。
  所以轮询**从不编码**（`readImage()` 返回一个惰性句柄，`toPng()` 带 memo），
  且图片**每 3 个 tick 才读一次**（文本每 tick 都读）。
- **文本优先**：浏览器「复制图片」时往往同时往剪贴板塞文本和位图，
  若按图片处理，粘出来会莫名其妙变成一张图。所以两者都在时按文本处理。

**验证**：`test/clipboard-units.js`（0.2.8 时 34 项，0.2.12 扩到 45 项，见 §11.4）—— 文本不变、同一张图只发一次且不重编码、
不同图会发、**会重编码的后端不会回声**、字节哈希的回退路径、`imageEvery` 的节奏、
接收侧的 caps / PNG 魔数 / 超限 / 坏图处理、一个真实 socket 对跑能力协商、
以及「没有 `caps` 的老客户端被当作纯文本接受」。

### 9.3 Wayland 原生采集（`src/capture-evdev.js` + `src/capture.js`）

**动机**：0.2.6/0.2.7 解决的是**注入**（client 侧）。但**捕获**（server 侧）在 Wayland 下
原本靠 uiohook 走 Xwayland 勉强能用，前提是**只有当某个 X11 窗口有焦点时**才收得到事件。
用户一碰原生 Wayland 应用，server 就瞎了 —— 表现是「明明在推鼠标，对端却不动」。

**做法**：直接读内核的 `/dev/input/event*`（evdev），不经过任何显示服务器。
`input.capture` 默认 `auto`：Windows / X11 用 uiohook，**Wayland 自动切 evdev**。
后端抽象进 `capture.js`（`chooseCapture` + 统一接口），`server-input.js` 不再直接依赖 uiohook。

几个必须知道的内核细节：

- **`struct input_event` 在 64 位进程是 24 字节、32 位是 16 字节** ——
  尺寸要跟**进程 ABI**，不是内核的构建目标。偏移从尾部读（`size-8` / `size-6` / `size-4`），
  这样 timeval 的宽度永远不影响解析。
- **按 `EV_SYN`/`SYN_REPORT` 分帧**：一次物理报告是一串事件 + 一个 `SYN_REPORT` 结尾。
  这样分帧，斜向拖拽才是斜线而不是阶梯；分帧内的发射顺序是 移动 → 按键 → 滚轮 → 键盘，
  这样点击落在用户瞄准的位置。
- **`REL_WHEEL_HI_RES` 要忽略**：高分辨率滚轮会**同时**报 `REL_WHEEL=1` 和
  `REL_WHEEL_HI_RES=120`，两个都算会一格滚 121 格。只认 `REL_WHEEL`，与 uiohook 的「格」语义一致。
- **过滤我们自己的虚拟设备**：读到自己 uinput 注入设备创建的事件，会把注入的位移当成用户输入读回来
  （`OUR_DEVICE_PATTERNS`）。

**evdev 读不到光标的绝对位置** —— Wayland 出于安全**刻意不暴露**指针坐标，只给相对位移。
所以：

- server 端的「光标在哪」是**自己积分出来的**（`setAnchor` 定锚点 + 累加位移）；
- 「推到屏幕边缘」这个判据失效 → **触发方式改成手势**：**持续朝某一边推**
  （累计约屏短边的 35%，至少 200px）就交出去（`pushTarget()`）；
- 好处是顺带**干掉了整套「回中」逻辑**（`jumpLimit` / `recenterCursor`）——
  物理光标从不被挪动，也就不会被屏幕边缘夹住。

**权限**：`/dev/uinput`（注入）和 `/dev/input/event*`（采集）都在 `input` 组，
所以 `install-linux.sh --uinput` 现在写**两条** udev 规则，一次修好两件事，之后注销重登一次即可。
`doctor.js` 新增 **Server-role capture** 一节，报告选中的后端、警告 evdev 没有绝对位置、
并在 evdev 不可用时给出**确切的修法**（复用了 uinput 那套三形态权限判断）。

**兜底优先于报错**：首选后端起不来时自动换另一个，并在日志里**大声说明为什么** ——
因为「完全没有捕获」比「用错后端」更糟（后者至少还能动，只是有前提）。
例如 Wayland 上 evdev 失败回退到 uiohook，日志会写明「只在 X11 窗口有焦点时有效」。

**验证**：`test/capture-units.js`（35 项）—— 24/16 字节记录、尾部半条记录、
一次报告合成一帧、跨 chunk 的分帧、帧内顺序、BTN_ 映射、自动重复被丢、
垂直/水平滚轮、`REL_WHEEL_HI_RES` 被忽略、`EV_ABS` 被忽略、`/proc/bus/input/devices` 解析、
`bitmapHas` 两种词序、自有设备过滤、后端 start/anchor/detach/无设备/失败/stop/status、
`chooseCapture`，以及回退时**日志里要有原因和权限提示**。传输层用假 `readdir`/`readFile`，不需要 Linux。

## 10. 阶段十：注入后端真的能用（0.2.11）

> **版本沿革先说清楚**：`0.2.9`（文件 / 文件夹剪贴板）和 `0.2.10`（ydotoold 多路径探测）
> 都已**废弃并回退**，产物从 `dist/` 与共享目录里删掉了。`0.2.11` = **0.2.8 + 本节的注入修复**，
> 不包含那两个版本里的任何东西。回退是靠会话文件快照 + 旧 `app.asar` 逐字节比对做的，
> 见 §14 第 89 条。

### 10.1 现象：守护进程活着，报告说它不存在

用户 Ubuntu 那台（Wayland，2560×1440）发来的 `--injecttest` 报告，注入全挂，唯一线索是：

```
最近一次失败：ydotoold 不可用：3000ms 内没有出现可连接的 socket
               （/run/user/<uid>/.netmouse-ydotoold-<pid>.sock）
```

四个观测同时成立：

- **进程没有退出**（没有 `exit` 事件）
- **没有 stderr**（它没报错）
- **进程还活着**（`kill` 之前一直在）
- **我们要的位置没人应答**

当时的判断是「它忽略了 `--socket-path`，绑到默认位置去了」，于是做了 0.2.10（同时盯住所有
已知位置）。**那个判断是错的**：它确实绑在了我们请求的路径上，只是**我们探测的方式根本不成立**。

### 10.2 根因：`SOCK_DGRAM` 的 socket 不能用 `SOCK_STREAM` 去探

`ydotoold` 的 socket 是 **`SOCK_DGRAM`**。而探测用的是：

```js
net.connect({ path: socketPath })   // 建的是 SOCK_STREAM
```

内核直接拒绝，`connect()` 立刻以 `EPROTOTYPE: Protocol wrong type for socket` 失败。
于是：

- **守护进程活得好好的，探测永远返回 false**；
- 3 秒后 `spawnOwn()` 走失败分支，`c.kill()` —— **亲手杀掉一个完全能用的守护进程**；
- 报告、日志、UI 全部一致地说「socket 没出现」，**每一个观测都在说谎，而且彼此自洽**。

这是 §14 第 51 条（`.catch(() => {})`）的第二次发作，形态更隐蔽：
**代码没错、错误没被吞、日志也没写错 —— 错的是「用什么手段去观测」。**
以后遇到「进程活着 / 没退出 / 没 stderr / 我要的东西不在」四种观测同时成立，
**先怀疑探测手段本身**，而不是继续加探测点。

### 10.3 修法

1. **探测改成让真客户端去问**：`ydotool debug` 的退出码为 0 才算活着（`socketAlive()` 因此
   从 `Promise<boolean>` 变成同步 `boolean`，`spawnSync` 带 250ms 超时）。
   顺手把 `ydotool debug` 的 stderr 记进 `probeError()`，失败时拼进报告。
2. **随程序附带 `ydotool` / `ydotoold`**（`resources/bin/`，共 43 KB）：
   `bin/` 由 `linux.extraResources` 拷进成品包，`resolveBin()` 优先用系统版、找不到才用附带版。
   - **为什么系统版优先**：附带的是按 **glibc 2.34** 编的，Ubuntu 20.04 / Debian 11（2.31）
     上加载会直接报 `version 'GLIBC_2.34' not found`。附带是「本来什么都没有」的兜底，不是升级。
   - 解析结果**按二进制名缓存**：注入器每个动作都要 spawn 一次，每次再 fork 一个 `which`
     在 60Hz 的鼠标移动下是不可接受的。
3. **滚轮**：`ydotool` 没有滚轮子命令（manpage 只有 `type`/`key`/`mousemove`/`click`/`stdin`），
   所以 `bin/wheel.py` 直接往 `/dev/uinput` 写 `REL_WHEEL` / `REL_HWHEEL`。
   `TOOLS.ydotool.wheel` 因此从 `false` 变成 `true` —— 注意 `ydotoolArgs()` 仍然对滚轮返回
   `null`：**「命令不存在」和「能力不存在」是两件事**，混为一谈正是原来的错。
4. **失败信息带证据**：`守护进程：<实际路径>` / `客户端：<实际路径>` / `探测结果：<stderr 或 exit code>`。
5. **`--injecttest` 不再自相矛盾**：顶部 `ydotoold：未检测` 改成「还没拉起 —— 下面的测试会
   先把它拉起来」，并在结论前打印 **ydotoold 最终状态**。
6. **`--doctor` 打印用的是哪一份二进制**（bundled / system）和它的绝对路径。

### 10.4 验证结果（0.2.11）

`npm test` 十二块全绿（本机 Windows 实测）：

```

CLIPBOARD-UNITS 34/34 · CAPTURE-UNITS 35/35 · DIAGBUNDLE-UNITS 18/18 ·
UINPUT-UNITS 39/39 · YDOTOOLD-UNITS 37/37 · UI CHECK PASS · HWTEST-UNITS 17/17 · E2E 39/39
```

新增/改写的断言（都能抓到旧行为）：

  所以只有断言形状才能钉住它。

## 11. 阶段十一：图片传输格式扩展（0.2.12）

### 11.1 起因：一句「图片只支持 png 吗」

界面上的勾选项写着「同时同步剪贴板里的图片（PNG）」、提示行写着「图片按 PNG 传输」，于是有了这个问题。
回答它之前要先把两件常被混为一谈的事分开：

| | 是不是只有 PNG |
| --- | --- |
| **你复制的图片** | **不限格式**。剪贴板交出来的是**位图**（`clipboard.readImage()` → `nativeImage`），JPEG / PNG / WebP / BMP / GIF 首帧、系统截图全都一样。程序拿不到「原文件格式」，也不需要 —— 它只看到像素 |
| **线上传输的编码** | **只有 PNG**（0.2.11 及更早）。这是刻意的：无损、各平台都能解 |

所以「格式不够多」本身不是问题，**只有一个格式**才是 —— 因为 PNG 对**照片**极其不友好。

### 11.2 量出来的代价

真 Electron 31 探针（临时脚本，测完删掉），2400×1800（4.3 MP）随机噪声填充 ——
噪声是对 PNG 最不利、也最接近照片细节的极端情况：

| 编码 | 大小 |
| --- | ---------- |
| PNG | **12.38 MB** |
| JPEG q92 | 3.61 MB |
| JPEG q85 | 2.94 MB |
| JPEG q78 | 2.52 MB |
| JPEG q70 | 2.17 MB |
| JPEG q60 | 1.83 MB |

默认上限 8 MB，于是这张图在旧版里**被整张丢弃**。用户看到的现象是
「复制了一张照片，对面什么都没发生，日志里只有一行『过大』」。按同样的像素密度推算，
12 MP 手机照片（4000×3000）的 PNG 约 34 MB —— 一样丢。

反向的数据同样重要：800×600 的平滑渐变图，PNG **11,346 B**、JPEG q85 **13,645 B**，
**PNG 更小**。截图、图表、带文字的画面都是这个方向。所以正确的策略不是「改成 JPEG」，
而是**先 PNG，塞不下才降级**。

### 11.3 改法

1. **两种线上格式**：`format: "png" | "jpeg"`。发送端先 `toPNG()`；只有超限才 `toJPEG(q)`，
   质量阶梯 `[92, 85, 78, 70, 60]`，取**第一个能塞进去**的档 —— 不是无脑用最低档。
2. **能力分开声明**：`CAPS = ["img", "jpg"]`。`img` 表示懂图片（0.2.8+），`jpg` 表示懂 JPEG（0.2.12+）。
   0.2.8–0.2.11 懂图片但只懂 PNG，给它们发 JPEG 会**白传一趟再被丢掉**，所以对端没 `jpg` 就只发 PNG，
   超限照旧丢弃 —— 但警告里必须说明**为什么**（`未同步：对端未声明 JPEG 能力`），
   否则和「图太大」看起来一模一样。
3. **接收端只认两种，且标签必须和载荷一致**：`normalizeImageFormat()` 先把
   `jpeg` / `jpg` / `image/jpeg` 归一成 `jpeg`（拼写差异不该算格式不兼容），再用
   `FF D8 FF` / PNG 签名分别校验；**标签与魔数不符就拒收**（`format:"png"` 而载荷是 JPEG 也拒）。
   不把未知字节喂给解码器去「自己看着办」。
4. **降级要留下数字**：所有档位都超限时，警告写的是**最小那次尝试**（`已降到 JPEG q60`），
   而不是一句「过大」—— 否则用户会以为是自己把上限设小了。
5. **后端能力要判而不是假设**：`nativeImage.toJPEG` 不存在时不能假设存在，
   `typeof === "function"` 才挂 `toJpeg`；没有就退回「PNG 或丢弃」，不抛错。
   （Electron 的命名也不一致：`toPNG` / `toJPEG` 全大写，`toBitmap` 是驼峰 ——
   写成 `toJpeg` 会得到 `undefined`，而 `typeof` 判断会把它**静默**读成「后端不支持 JPEG」。）
6. **接口改名**：`writeImage({ png })` → `writeImage({ data, format })`。
   传 JPEG 的字段叫 `png` 是在说谎，而「名字必须带语义」是本项目的老规矩
   （与「几何 API 函数名必须带单位」同源）。

### 11.4 验证

- `CLIPBOARD-UNITS` **34 → 45**。新增 11 条：PNG 够小就不碰 JPEG（断言 `jpegEncodes === 0`）、
  超限转 JPEG 后真的发出去、质量阶梯**只走到第一个够用的档**（断言实际尝试序列是 `[92,85,78]`）、
  无 `jpg` 能力时不编码只丢弃且警告点名原因、后端无 `toJPEG` 时不假装、全档超限时警告里带 `q60`、
  收到 JPEG 能写入且不回声、`jpeg`/`jpg`/`image/jpeg` 别名、**标签与载荷不符双向拒收**、
  `normalizeImageFormat`/`isJpeg` 的表驱动检查、握手两端都声明 `img`+`jpg`。
- **真 Electron 探针（这轮最要紧的一条）**：`imageKey(bytes)` 必须等于
  「写进剪贴板再读回来」算出的键，否则**有损编码会破坏回声抑制**，两端互推。实测 PNG / JPEG **两种都成立**。
- 另一条实测事实：Windows 上 `writeImage()` 之后 `availableFormats()` 只报 `["image/png"]` ——
  **即使写进去的是 JPEG**。剪贴板里存的始终是位图，所以接收端下一轮读到的与线上格式无关，
  这也顺带证明了「读的是像素」这个模型是对的。

### 11.5 仍未验证

- **没有真机跑过跨机 JPEG 同步**（与 0.2.8 的图片剪贴板同一个坑：需要第二台机器）。
- `toJPEG` 在 Linux/Electron 31 上的行为**假定**与 Windows 相同（同一个 Chromium 解码器，但没跑过）。
- 未测超大图（>50 MP）的编码耗时。最坏情况是 1 次 PNG + 5 次 JPEG 编码，
  按每档 20–40 ms 估，单次切换多花约 200 ms —— 只在图片**变化时**发生一次，不在轮询里。

## 16. 附录：可复用的验证手法

1. **验证打包后的模块加载**（纯托盘应用不能直接启动，会挂全局键鼠钩子）
   ```bash
   ELECTRON_RUN_AS_NODE=1 NetMouse.exe -e "require('...app.asar/src/config.js').loadConfig()"
   ```
2. **离屏渲染界面截图**：临时 Electron 脚本 + stub preload + `capturePage()`。
3. **真机 E2E（CDP）**：
   ```bash
   NetMouse.exe --remote-debugging-port=9223
   ```
   再用 Node 22 内置 `WebSocket` 连 `http://127.0.0.1:9223/json/list` 拿  
   `webSocketDebuggerUrl`，走 `Runtime.evaluate` 调 `window.netmouse.*`。  
   注意 `await` 要包在 async IIFE 里，且用 `NETMOUSE_CONFIG` 指向临时配置。
4. **CDP 截图**：同一个连接调 `Page.captureScreenshot`，直接存 PNG。
5. **静态校验 Linux 包**：`python3 scripts/verify-linux-portable.py`  
   （权限位 / ELF magic / 自解压偏移 / 内嵌流一致性 / `sh -n`）。
6. **模拟「已打包」的配置解析**：直接单测 `config.resolveWritePath(asarPath, {userDataDir})`，  
   因为开发目录里的 `config.json` 是可写的，会掩盖 `app.asar` 只读的真实情况。
7. **测只有主进程才能做的事（窗口/遮罩）**：写一个临时 Electron 脚本，  
   `app.whenReady()` 后 `require` 项目里的模块直接调，用 `BrowserWindow.getAllWindows()`  
   断言窗口数量、`getBounds()` 断言覆盖范围。注意脚本里要加  
   `app.on("window-all-closed", () => {})`，否则窗口关掉时脚本自己会退出。
8. **测协议/同步逻辑而不启动 GUI**：直接用 `startServer` + `connectClient` 起真实 socket，  
   把 `io`/`send` 换成假实现（`clipboard.js`、`hotkey.js`、`config.js` 都为此留了可注入点），  
   就能在纯 Node 下断言双向同步、回声抑制、退避重连等行为。
9. **纯函数优先**：热键解析、显示器解析、坐标换算、剪贴板回声判断都做成纯函数或可注入，  
   这样 `selftest.js` 一条命令就能覆盖，不必每次起 Electron。
10. **端到端回环（本机验证跨机逻辑，不需要第二台机器）**：  
    用 `--require test/mock-native.js` 把 `uiohook-napi` / `@nut-tree-fork/nut-js` /  
    `./platform` 换掉（写进 `require.cache` 即可，不用改业务代码），  
    然后**真起两个进程**：一个 `--role server`、一个 `--role client`，走**真 TCP**。  
    两个进程用 stdin/stdout 的 JSON 行通信：父进程发 `{"cmd":"hand","dx":..}` 驱动"手部位移"，  
    子进程回 `{"ev":"calls"}` 报告"注入动作"。  
    关键在**替身的指针模型要像真 OS**：手部位移会移动光标并被桌面边界**夹住**，  
    `setPosition` 是瞬移 —— 这样才测得出"行程不够"这类真实约束。  
    起手先跑一遍**基线**，让断言去暴露 bug，而不是只验证"能跑通"。
11. **只差平台的部分做成体检脚本**：本机没有的东西（X11 库、DISPLAY、xdotool、注入权限）  
    不要靠猜，写进 `src/doctor.js`，让用户在目标机上一条命令得到 `✓/!/✗` 和修复命令。
